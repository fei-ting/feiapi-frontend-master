# 依赖安全与必要性整改设计

## 背景

前端工程当前使用 Yarn Classic 1.22.22 和 `yarn.lock` 管理依赖。审查期间使用当前锁文件执行 `audit-ci` 未发现已登记的已知漏洞，但该检查尚未进入持续集成流程，代码不变时新披露的漏洞也无法被定期发现。

`package.json` 将 `dayjs` 声明为直接运行时依赖，但对 `src`、`public`、入口文件和构建配置的静态检索均未发现直接引用或运行时动态加载。`yarn why dayjs` 显示它同时来自项目直接声明和 `ant-design-vue` 的间接依赖，因此删除直接声明不会从最终依赖树中移除 Ant Design Vue 所需的 `dayjs`。

仓库目录中还存在本地生成的 `package-lock.json` 和 `pnpm-lock.yaml`，两者均已被 `.gitignore` 忽略且未被 Git 跟踪。本次整改不操作开发者本地的忽略文件，仓库继续只以 `yarn.lock` 作为依赖锁文件。

## 目标

1. 删除未被业务源码直接使用的 `dayjs` 直接依赖，保持 Ant Design Vue 的间接依赖完整。
2. 使用固定版本的安全审计工具，对中危、高危和严重漏洞阻断持续集成。
3. 在安装项目依赖前执行安全审计，降低执行存在风险的依赖安装脚本的机会。
4. 在日常持续集成之外每周执行一次审计，以发现新披露但尚未触发代码变更的漏洞。
5. 保持页面功能、类型边界、测试覆盖率和生产构建结果不变。

## 非目标

- 不升级 TypeScript、Vite、Vue、Pinia、Vue Router 或其他现有依赖。
- 不删除 `ant-design-vue` 间接使用的 `dayjs`，也不通过包管理器覆盖强制改变其版本。
- 不引入自动依赖升级工具或自动合并机器人。
- 不为通过审计预先设置漏洞白名单。
- 不清理未被 Git 跟踪的本地 `package-lock.json` 和 `pnpm-lock.yaml`。
- 不调整业务代码、页面交互、视觉样式、接口契约或路由。

## 方案比较与决策

### 方案一：固定版本命令加独立配置

通过 `npx` 执行固定版本 `audit-ci@7.1.0`，审计策略写入仓库内的 `audit-ci.jsonc`，并提供统一的 Yarn 脚本供本地和 CI 调用。

优点是不会扩大项目常驻依赖树，工具版本和审计策略均可复现，CI 也能在安装项目依赖前完成检查。缺点是每次审计需要从注册源获取审计工具，但工具获取或审计源异常时会明确失败，不会静默放行。

### 方案二：将审计工具加入开发依赖

把 `audit-ci` 固定为开发依赖后通过本地二进制执行。该方案减少重复下载，但会扩大锁文件和依赖树，并要求先安装项目依赖后才能审计，不符合安装前检查的目标。

### 方案三：仅在工作流内写命令参数

直接在 GitHub Actions 中执行带阈值参数的审计命令。该方案文件改动较少，但策略分散在工作流中，缺少统一的本地复现入口，后续调整和审查也更容易遗漏。

本次采用方案一。

## 依赖必要性整改

从 `package.json` 的 `dependencies` 删除 `dayjs`。同步调整 `yarn.lock`，移除项目直接声明产生的 `dayjs@^1.11.13` 选择器，保留 `ant-design-vue` 所需的 `dayjs@^1.10.5` 条目及其实际解析版本。

整改后通过源码检索和 `yarn why dayjs` 双重核验：

- 源码仍不存在对 `dayjs` 的直接调用。
- 依赖原因仅剩 `ant-design-vue#dayjs`。
- 冻结锁文件安装能够通过，证明依赖声明与锁文件一致。

## 安全审计策略

新增 `audit-ci.jsonc`，策略如下：

1. 显式使用 Yarn 作为被审计的包管理器。
2. 将 `moderate` 设为阻断阈值，因此中危、高危和严重漏洞均导致命令失败。
3. 使用摘要报告，保留漏洞标识和失败原因，同时控制 CI 日志体积。
4. 初始白名单为空；发现漏洞后应优先升级或替换依赖。确需临时放行时，必须单独评估影响范围、记录漏洞编号和移除条件。
5. 不启用审计源不可用时放行；无法完成审计视为安全门禁失败。

`package.json` 新增 `audit:dependencies` 脚本，统一执行固定版本 `audit-ci@7.1.0` 和上述配置。固定精确版本可避免审计工具自身发生未评估的行为变化。

## 持续集成设计

现有前端 CI 保持单一工作流，在 Node.js 环境准备完成后、`yarn install --frozen-lockfile` 之前执行依赖安全审计。调整后的顺序为：

```text
检出代码
  -> 设置 Node.js
  -> 依赖安全审计
  -> 冻结锁文件安装
  -> TypeScript 类型检查
  -> 单元测试与覆盖率门禁
  -> 生产构建
```

工作流继续响应 `dev`、`main`、`master` 的推送和拉取请求以及手动触发，并增加每周一定时执行。定时任务使用 UTC 02:00，即北京时间 10:00；GitHub Actions 的定时任务只在默认分支上运行，可在没有代码提交时发现审计源中新登记的漏洞。

安全审计失败后不会安装项目依赖，也不会继续执行测试和构建。网络或审计源短暂异常由 `audit-ci` 自带重试机制处理；重试后仍无法完成审计则保留失败状态，避免把“未完成检查”误报为“没有漏洞”。

## 测试与验收

1. 执行源码全量检索，确认没有 `dayjs` 的静态导入、动态导入或 CommonJS 加载。
2. 执行 `yarn install --frozen-lockfile`，确认 `package.json` 与 `yarn.lock` 一致。
3. 执行 `yarn why dayjs`，确认它仅由 `ant-design-vue` 间接引入。
4. 执行 `yarn audit:dependencies`，确认当前锁文件未命中中危及以上已知漏洞。
5. 执行 `yarn typecheck`，确认类型检查通过。
6. 执行 `yarn test` 和 `yarn coverage`，确认现有行为及覆盖率门禁不回退。
7. 执行 `yarn build`，确认 Vue 类型检查和 Vite 生产构建通过。
8. 检查 Git 差异，确认本地忽略的其他包管理器锁文件未进入提交。

## Git 流程

1. 从前端 `dev` 分支创建 `feature/dependency-security-necessity`。
2. 先提交本设计文档。
3. 用户复核设计后，再完成依赖声明、锁文件、安全策略和持续集成修改。
4. 通过安全审计、类型检查、全量测试、覆盖率门禁和生产构建后提交实现。
5. 完成代码审查后合并回 `dev`。
6. 删除临时 feature 分支。
