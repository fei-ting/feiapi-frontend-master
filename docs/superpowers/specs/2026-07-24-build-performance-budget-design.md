# 构建性能预算整改设计

## 背景

前端工程已经对所有路由页面使用动态导入。接口广场每页请求 6 条数据，后台接口列表每页请求 10 条数据；页面图片主要是顶部导航和个人资料区域的首屏用户头像。当前页面规模没有支持引入虚拟滚动、图片懒加载或手工分包的证据。

2026-07-24 使用最新生产构建产物重新测量得到以下基线：

| 指标 | 当前值 |
| --- | ---: |
| 构建文件数量 | 53 个 |
| 全部文件未压缩总量 | 428,733 字节 |
| 逐文件 Gzip 体积合计 | 162,168 字节 |
| 最大 JavaScript 未压缩体积 | 151,970 字节 |
| 最大 JavaScript Gzip 体积 | 56,906 字节 |

当前最大 JavaScript 分块明显低于 Vite 默认的 500 KB 分块警告阈值，完整应用体积也未显示紧迫的性能风险。但是 CI 只构建和上传产物，不记录上述指标，也无法识别后续提交造成的异常增长。

## 目标

1. 使用可重复的方式记录完整构建体积、Gzip 体积和最大 JavaScript 分块体积。
2. 相对基线增长达到 10% 时在 CI 中产生明确警告，但不阻断正常开发。
3. 相对基线增长达到 25% 时使 CI 失败，阻止未评估的性能回退。
4. 在 GitHub Actions 任务摘要中展示当前值、基线值、增长比例和检查结论。
5. 不引入新的第三方依赖，不改变业务页面、路由拆分、分页、图片加载和 Vite 默认分包行为。

## 非目标

- 不把完整构建体积等同于首屏下载体积。
- 不引入 Lighthouse 或依赖浏览器、网络和后端响应的性能评分。
- 不增加虚拟滚动、图片懒加载、预加载或预取策略。
- 不配置 `manualChunks`，也不人为拆分 Vue、Ant Design Vue 等公共依赖。
- 不启用 Source Map、Brotli 产物或额外的压缩构建插件。
- 不改变接口分页数量、页面交互、视觉样式或接口契约。
- 不自动更新性能基线，避免为了通过门禁而掩盖真实增长。

## 方案比较与决策

### 方案一：零依赖 Node.js 性能预算脚本

使用 Node.js 标准库遍历 `dist`，通过 `zlib` 计算逐文件 Gzip 体积，读取仓库内的性能预算配置并输出 CI 摘要。

该方案不扩大依赖树，计算过程可测试、可复现，能够同时覆盖总量和最大分块，也可以准确实现两级阈值。代价是需要维护一段规模较小的项目脚本。

### 方案二：引入 `size-limit` 等第三方工具

现成工具配置简洁、生态成熟，但会新增直接开发依赖和一组间接依赖。当前需求只涉及文件遍历、Gzip 计算和阈值比较，Node.js 标准库已经足够，新增依赖的收益不足以抵消维护和安全成本。

### 方案三：只使用 Vite 默认分块警告

该方案无需增加脚本，但只能关注单个分块，默认阈值较高，不能记录完整构建体积、Gzip 总量或相对基线增长，也无法对 10% 和 25% 两级策略做出不同处理。

本次采用方案一。

## 性能预算配置

新增根目录 `performance-budget.json`，记录四项基线和两级增长比例：

```json
{
  "baseline": {
    "totalRawBytes": 428733,
    "totalGzipBytes": 162168,
    "largestJavaScriptRawBytes": 151970,
    "largestJavaScriptGzipBytes": 56906
  },
  "warningGrowthRate": 0.1,
  "failureGrowthRate": 0.25
}
```

四项指标分别保护完整产物规模、完整网络压缩规模、最大 JavaScript 分块规模和最大分块的压缩规模。任何一项达到警告或失败比例，整体结论就进入对应级别。

警告线和失败线按基线实时计算，不在配置中重复保存派生数字，避免修改基线时遗漏对应阈值。当前基线对应的阈值约为：

| 指标 | 10% 警告线 | 25% 失败线 |
| --- | ---: | ---: |
| 未压缩总量 | 471,606 字节 | 535,916 字节 |
| Gzip 总量 | 178,385 字节 | 202,710 字节 |
| 最大 JavaScript 未压缩体积 | 167,167 字节 | 189,963 字节 |
| 最大 JavaScript Gzip 体积 | 62,597 字节 | 71,133 字节 |

有合理业务原因需要提升基线时，应在同一变更中记录调整前后数据和原因，并接受代码审查；脚本不提供自动重写基线的参数。

## 体积检查脚本设计

新增 `scripts/check-build-size.mjs`，仅使用 `node:fs`、`node:path`、`node:url` 和 `node:zlib`。

脚本职责拆分如下：

1. 读取并校验性能预算配置，要求基线为正整数、警告比例大于 0、失败比例大于警告比例。
2. 递归读取 `dist` 中的全部文件；目录不存在、目录为空或不存在 JavaScript 文件时给出明确错误并失败。
3. 计算每个文件的原始字节数和 Gzip 字节数，汇总总量，并分别识别未压缩体积最大和 Gzip 体积最大的 `.js` 文件。
4. 逐项计算 `(当前值 - 基线值) / 基线值`，下降或未增长的指标按实际负增长展示，不产生警告。
5. 任一指标达到 25% 时记录失败；没有失败但任一指标达到 10% 时记录警告；其余情况通过。
6. 在本地终端输出中文表格和结论；存在 `GITHUB_STEP_SUMMARY` 环境变量时追加 Markdown 摘要。
7. 警告级别在 GitHub Actions 输出 `::warning::`，进程保持成功；失败级别输出错误并将退出码设为 1。

脚本不会把报告文件写入 `dist`，避免统计结果影响下一次计算。文件名包含构建哈希时仍按扩展名识别最大 JavaScript，不依赖固定名称。

## 测试设计

新增 `scripts/check-build-size.test.mjs`，使用项目现有 Vitest 覆盖以下场景：

1. 正常收集嵌套目录文件并正确计算原始体积、Gzip 体积，且能识别两种口径下不同的最大 JavaScript 文件。
2. 所有指标低于 10% 时返回通过。
3. 任一指标达到 10% 且低于 25% 时只返回警告。
4. 任一指标达到 25% 时返回失败，且失败优先于其他指标的警告。
5. 当前值低于基线时显示负增长但不产生警告。
6. 构建目录不存在、为空或没有 JavaScript 文件时明确失败。
7. 配置包含非正基线或无效阈值关系时明确失败。
8. 当前构建指标缺失或无效时失败关闭，不会因 `NaN` 比较误判为通过。
9. 命令行在警告级别返回退出码 0，在失败级别返回退出码 1。

测试文件位于 `scripts`，现有覆盖率配置只统计 `src`，因此不会改变业务源码覆盖率口径，但会随 `yarn test` 和 `yarn coverage` 一同执行。

## 持续集成设计

`package.json` 新增 `check:size` 脚本：

```text
node scripts/check-build-size.mjs
```

现有 CI 在 `yarn build` 成功后、上传 `dist` 前执行 `yarn check:size`：

```text
依赖安全审计
  -> 安装依赖
  -> 类型检查
  -> 单元测试与覆盖率
  -> 生产构建
  -> 构建体积门禁
  -> 上传构建产物
```

构建失败时不会执行体积检查；体积检查达到失败线时不会上传该次构建产物。警告不会改变退出码，仍保留产物供进一步分析。

## 验收标准

1. `yarn build` 成功生成生产构建产物。
2. `yarn check:size` 能稳定复现四项当前基线并返回通过。
3. 临时测试数据能够证明 10% 警告和 25% 失败边界生效，正式基线不因测试被修改。
4. `yarn test` 和 `yarn coverage` 包含新增脚本测试并全部通过。
5. `yarn typecheck` 通过，现有 Vue 和 TypeScript 代码不受影响。
6. CI YAML 格式检查通过，体积门禁位于生产构建之后、产物上传之前。
7. `yarn audit:dependencies` 继续通过，本次不新增依赖。
8. Git 差异不包含 `dist`、临时报告或其他生成文件。

## 实现与验证结果

2026-07-24 已按本设计完成实现，实际结果如下：

- 新增零依赖构建体积检查脚本，使用 Node.js 标准库统计完整产物和最大 JavaScript 的原始、Gzip 体积。
- 最大未压缩 JavaScript 和最大 Gzip JavaScript 分别识别，即使两种口径对应不同文件也不会漏报。
- 新增性能预算配置，四项基线与本次生产构建完全一致；增长达到 10% 时警告，达到 25% 时失败。
- 本地终端输出和 GitHub Actions Markdown 摘要生成逻辑均已实现；脚本不写入 `dist`，也不自动修改基线。
- CI 已在生产构建后、上传构建产物前执行 `yarn check:size`。
- 性能脚本 15 个单元测试全部通过，覆盖目录遍历、双口径最大分块、阈值边界、失败优先级、负增长、无效目录、无效配置、指标失败关闭和命令行退出码。
- `yarn check:size` 通过：53 个文件，未压缩总量 428,733 字节，Gzip 总量 162,168 字节，最大 JavaScript 未压缩体积 151,970 字节，最大 JavaScript Gzip 体积 56,906 字节，四项相对基线均为 0%。
- CI YAML 和两个 `.mjs` 脚本语法检查通过。
- `yarn audit:dependencies` 通过，本次没有新增第三方依赖。
- `yarn typecheck` 通过。
- `yarn test` 通过，46 个测试文件、259 个测试全部通过。
- `yarn coverage` 通过，46 个测试文件、259 个测试全部通过，覆盖率门禁未回退。
- `yarn build` 通过，Vue 类型检查和 Vite 生产构建成功。

覆盖率命令仍会尝试解析本地被 Git 忽略的历史 `.umi` 和 `.umi-production` 生成目录并输出排除警告，但命令最终通过。这些目录未进入本次提交，警告不是本次性能预算整改引入的问题。

## Git 流程

1. 从前端 `dev` 分支创建 `feature/build-performance-budget`。
2. 先提交本设计文档。
3. 用户复核设计后，再实现性能预算配置、检查脚本、单元测试和 CI 门禁。
4. 通过安全审计、类型检查、全量测试、覆盖率门禁、生产构建和体积门禁后提交实现。
5. 完成代码审查后合并回 `dev`。
6. 删除临时 feature 分支。
