# 覆盖率统计范围与质量基线清理设计

## 背景

项目已从 React + Umi 迁移到 Vue 3 + Vite，但本地仍可能保留被 `.gitignore` 忽略的 `src/.umi` 和 `src/.umi-production` 生成目录。当前 Vitest 覆盖率配置使用 `src/**/*.{ts,vue}` 收集运行时代码，没有排除这两个目录，导致部分 Umi 生成文件解析失败后被覆盖率工具排除，另一些生成文件以 0% 计入统计。

现有覆盖率命令虽然返回成功，但总体数据混入非业务生成代码，且全局门禁仍停留在语句 59%、分支 52%、函数 56%、行 60%，无法准确反映当前有效业务源码的质量基线。

## 整改目标

- 精确排除两个遗留 Umi 生成目录，保证覆盖率统计只包含预期的业务源码。
- 消除覆盖率执行过程中的 Umi 文件解析警告。
- 根据清理后的实际结果重新固化全局覆盖率门禁，防止整体覆盖率回退。
- 保持现有核心模块独立门禁不变。

## 非本次范围

- 不删除本地 `src/.umi` 或 `src/.umi-production` 目录。
- 不新增端到端测试框架或业务测试。
- 不调整具体业务模块的测试实现。
- 不修改 ESLint 或持续集成配置；相关问题在 11.3 单独整改。

## 方案比较

### 方案一：精确排除并同步提高门禁

在覆盖率排除项中增加 `src/.umi/**` 和 `src/.umi-production/**`，并以清理后的有效结果向下取整设置全局门禁。

优点是统计边界明确，既能消除生成代码污染，也能让门禁匹配当前真实水平。缺点是如果后续出现新的生成目录，需要显式补充排除规则。

### 方案二：精确排除但保留旧门禁

只增加目录排除规则，不调整全局门禁。该方案改动最小，但旧门禁明显低于当前有效覆盖率，不能有效阻止较大幅度的质量回退。

### 方案三：排除所有隐藏目录

通过 `src/.*/**` 统一排除隐藏目录。该方案配置简短，但可能误排未来有价值的隐藏目录，统计边界不够明确。

## 采用方案

采用方案一。

临时使用完整排除参数执行覆盖率后，46 个测试文件、259 个测试全部通过，未出现 Umi 解析警告，得到以下有效结果：

| 指标 | 实测结果 | 新全局门禁 |
| --- | ---: | ---: |
| 语句 | 79.35% | 79% |
| 分支 | 74.95% | 74% |
| 函数 | 74.81% | 74% |
| 行 | 79.85% | 79% |

全局门禁按实测结果向下取整，保留不足一个百分点的自然波动空间。现有核心模块门禁继续保持语句和行 90%、函数 85%、分支 80%。

## 配置设计

仅修改 `vite.config.ts`：

1. 在 `coverage.exclude` 中增加 `src/.umi/**`。
2. 在 `coverage.exclude` 中增加 `src/.umi-production/**`。
3. 将全局门禁调整为语句 79%、分支 74%、函数 74%、行 79%。
4. 不改变覆盖率提供器、报告格式、核心模块路径门禁和测试环境。

使用精确目录规则可以保证开发者本地是否残留 Umi 生成文件都不会影响覆盖率结果，同时不会扩大对其他源码的排除范围。

## 验证标准

依次执行以下验证：

1. `yarn coverage`：46 个测试文件和 259 个测试全部通过，Umi 生成文件不出现在覆盖率报告中，执行过程不再出现相关解析警告，所有门禁通过。
2. `yarn typecheck`：TypeScript 类型检查通过。
3. `yarn build`：生产构建通过。

覆盖率结果应不低于语句 79%、分支 74%、函数 74%、行 79%。如果结果低于门禁，应先查明测试或统计范围差异，不通过降低阈值绕过失败。

## 风险与控制

- 风险：排除规则拼写错误，生成目录仍被扫描。控制方式是保留本地生成目录并直接执行覆盖率，确认报告和日志中均不再出现相关文件。
- 风险：提高全局门禁后暴露环境差异。控制方式是在本地完成覆盖率、类型检查和构建，并在合并后由 Node.js 22 的 CI 再次验证。
- 风险：误改核心模块门禁。控制方式是仅调整全局四项数值，保持 `coreCoverageThresholds` 及其路径映射不变。
